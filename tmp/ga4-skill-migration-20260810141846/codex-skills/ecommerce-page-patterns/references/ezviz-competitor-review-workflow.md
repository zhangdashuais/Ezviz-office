# EZVIZ-First Product Detail Review Workflow

Use this workflow for requests such as "give interaction suggestions," "improve this product page," "audit the PDP," or "reference eufy/Reolink." Use the live, relevant regional source page whenever a URL is provided.

## Source Priority

1. The user's product page, assets, specifications, and target region.
2. The closest current EZVIZ international product page in the same category.
3. eufy for product-information grouping, feature-module layout, visual rhythm, and app/function presentation.
4. Reolink for technical proof, information hierarchy, and complex-feature explanation.

Do not recommend a pattern merely because a competitor uses it. Tie each pattern to a concrete purchase or understanding problem.

## Review Procedure

1. Classify the product: smart lock, doorbell, peephole viewer, indoor camera, outdoor camera, sensor/gateway, or video intercom.
2. Identify the page's main product-understanding question: "Will it fit?", "Can it see clearly?", "Will it work without power/Wi-Fi?", "Can I trust the notifications?", or "How does it connect with my home?"
3. Map the current EZVIZ sequence: hero, proof strip, key features, app/ecosystem, practical setup, privacy/storage, specs/support.
4. Record gaps as missing proof, unclear information hierarchy, unclear setup, hidden limitation, or weak page wayfinding.
5. Select a focused reference pattern:
   - eufy: quick-intro strip, feature grouping, image/text rhythm, app-state presentation, and model-comparison layout.
   - Reolink: sticky subnav, performance metrics, coverage diagrams, before/after comparisons, and detailed technology proof.
6. Propose the adapted interaction in EZVIZ visual language: calm whitespace, editorial bands, real home scenes, app UI, and restrained functional controls.
7. Check mobile behavior, accessibility, localization, asset requirements, and whether the page has factual content to support the claim.

## Recommendation Format

For each recommendation, use this format:

| Field | Include |
| --- | --- |
| Priority | P0 comprehension blocker, P1 meaningful information/interaction gain, or P2 polish |
| User problem | The question or uncertainty a visitor has |
| Preserve from EZVIZ | The visual/narrative convention that must remain |
| Adapt from competitor | eufy or Reolink pattern and why it is useful |
| Proposal | The interaction, content, and page position |
| Implementation | Native layout, CSS/JS, or asset/data requirement |
| Success signal | What becomes easier to understand or decide |

## Recommended Interaction Selection

| Situation | Prefer |
| --- | --- |
| Visual quality needs proof | Before/after slider, crop zoom, or side-by-side footage |
| Detection or automation is abstract | Trigger -> notification -> response flow with app UI |
| Product fit is risky | Compatibility selector, dimensions diagram, or installation decision path |
| Several models are similar | Task-led comparison table and model selector |
| App controls are a key value | Tabs for alert, live view, talk, privacy, playback, or access permissions |
| Long page has weak wayfinding | Sticky subnav with anchor progress state |
| A feature list feels dense or fragmented | Grouped proof strip, section anchors, or a focused information hierarchy |

## Guardrails

- Do not promise data, comparisons, performance, or integrations the product cannot substantiate.
- Keep interaction optional and useful. Avoid autoplay, decorative scroll effects, dense carousels, and hover-only information.
- Do not turn every feature into a card. Let visual proof and full-width story sections carry the page.
- Keep competitor references invisible in the final design unless the user explicitly asks for a benchmark report.
- Exclude checkout, pricing, delivery, returns, warranties, reviews, discounts, and purchase CTA optimization from competitor analysis unless the user explicitly requests them.
